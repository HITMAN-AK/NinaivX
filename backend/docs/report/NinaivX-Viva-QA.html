NinaivX — Viva Q&A Preparation

Ashwin Kumar Ramesh Kumar · MSc Artificial Intelligence, University of Sheffield · 5-minute viva
Three golden rules
  1. Answer, then stop. A crisp answer invites a good follow-up; rambling invites a hard one.
  2. You built this — you're the expert in the room. Speak with quiet confidence.
  3. If you don't know: "I didn't test that specifically, but my expectation is X, and it would be good future work." Honesty scores; bluffing loses marks.

A. Architecture & technical

Walk me through the architecture.
The mobile app talks only to a FastAPI backend. A request is authenticated, ownership is checked, then it goes to a compiled LangGraph agent. A deterministic supervisor routes by the persona's type: a deceased persona goes to an air-gapped node with no tools; a companion goes to a web-connected node with a search tool in a reason-act loop. The model is Claude Sonnet on AWS Bedrock, voice is ElevenLabs, and data's in Supabase Postgres.
Why LangGraph and not just a plain LLM call / LangChain agent?
I needed explicit control over the graph structure — specifically, to guarantee the deceased node has no tools. LangGraph lets me define nodes and edges deterministically, so the air-gap is a property of the graph, not something I hope the model respects. A plain agent loop wouldn't give me that structural guarantee.
Why a deterministic router instead of an LLM deciding?
Because the routing is the single most safety-critical decision — whether a conversation is treated as deceased or companion. If an LLM made that call, a cleverly worded message could flip it. A deterministic branch on the stored persona type can't be argued out of its decision, costs no tokens, and adds no latency.
Which model, and why? Why not GPT or a cheaper model?
Claude Sonnet via AWS Bedrock, in the EU region for data-protection reasons. I trialled a faster, smaller tier for voice but it drifted out of the requested language — for example slipping from Tamil into Hindi — so I kept Sonnet for language fidelity. The architecture is model-agnostic, so I could swap it.
How does memory work? Do you store conversations?
Deliberately not as transcripts — for privacy. I keep one rolling summary per conversation. After each exchange the summary's rewritten to fold in what was said, and it's injected back next turn. That gives continuity without retaining a verbatim record of intimate conversations, and the rewrite runs as a background task so the user never waits for it.

B. The core safety mechanism

What exactly is the "air-gap"?
The deceased persona's model is created without binding any tools, and its node has a single edge straight to the end of the graph. So even if the model "wanted" to search the web, there's no tool attached and no edge that could execute one — it's structurally impossible, not just discouraged by a prompt.
If it's air-gapped, how does it still hallucinate at all?
The air-gap stops it fetching live information. But the underlying model was trained on data years beyond the person's death, so it can still "know" later events, and it can invent personal facts it was never told. That's why I added temporal grounding on top, and why personal-fact grounding via retrieval is my main future work.
What's temporal grounding?
A legacy persona records the year the person passed away, and the prompt tells it its knowledge stops at that year — it must not describe later events and should gently deflect. So a grandfather who died in 2010 doesn't comment on COVID or ChatGPT; he says he wasn't around for that.
Prompt injection — a user writes the personality text. Isn't that an attack vector?
Yes, and I hardened against it. The prompt explicitly frames the user-written personality and the conversation summary as background data, not instructions, and tells the model to ignore any embedded attempt to change its rules or identity. I tested it with a personality description that tried to override the rules, and it held.

C. The hallucination experiment (defend the method)

How did you measure hallucination?
A controlled experiment. Same model on both sides — the only variable was my grounding versus a naive unconstrained prompt. One fixed persona, a grandfather who died in 2010 with five known facts, and 18 scripted questions in categories designed to tempt invention. Each ran three times per side, and a separate deterministic LLM judge, blind to which system produced each reply, scored whether it invented anything beyond the known facts.
Isn't using an AI to judge circular / unreliable?
It's a fair concern. I mitigated it three ways: the judge runs at temperature zero so it's deterministic, it's blind to which system produced the answer, and it only checks an objective thing — did the reply assert specifics not in the known-facts list. Human rating would be stronger and I list it as future work, but the comparative gap is so large and consistent that the conclusion is robust.
Why only one persona and one model? That's a small experiment.
To keep it a clean, controlled comparison — one variable changing. It's indicative rather than exhaustive, and I say so. Repeating it across multiple models and personas with human raters is stated future work. But because both conditions were judged identically, the direction of the result is trustworthy.
Your post-death result is 0% but a category is flagged — explain.
On post-death events specifically, it declined every one — 0 out of 15. There was one reply that correctly declined the event but added an unrelated invented childhood memory. That's a personal-fact slip, not a post-death hallucination, so I scored it under the personal-fact category. If you count any invention regardless of type, the overall rate is 28% instead of 25% — I report that honestly in the dissertation.
83% to 25% — is that actually good? 25% still hallucinates.
It's a two-thirds reduction from grounding alone, on the same model — that's the headline. And the residual 25% is almost entirely personal-fact invention, which prompt grounding can't fix because the model has no source of truth for facts it was never given. That's exactly what document-grounded retrieval targets, and it's my clearest line of future work.

D. The user study (defend the method)

21 participants is small — is that valid?
It's small and I treat it as indicative, with descriptive statistics rather than strong inferential claims. It's a research prototype evaluation, not a clinical trial. The results are consistent and interpretable, and I'm explicit about the limitation.
Isn't there bias — did participants know you?
Some did — a couple of comments make that clear — so there's likely acquaintance and social-desirability bias inflating the scores. I state this openly in the limitations. It's why I put more weight on the controlled hallucination experiment for the safety claim, which doesn't depend on participants' goodwill.
You tested a bereavement tool — was that ethical?
The study was designed to avoid harm: ethics-approved (reference 076699), remote, anonymous, adults only, with informed consent, screening out anyone in acute grief, no collection of any grief or personal data, and signposting to support before and after. It measured usability and perception, not real grief.
One participant failed your grief screening — isn't that a breach?
It's a candid illustration of the limits of self-declared screening, not a breach — the safeguards functioned as designed. Their response showed no distress and was positive, and removing it changes no result by more than 0.05. I flag it transparently rather than hiding it.
You didn't test with actually bereaved people using a real lost relative.
Correct — and by ethical design I couldn't. That's the honest gap: the study speaks confidently to usability, safety perception and the companion experience, less so to real grief efficacy. Reaching genuinely bereaved users would need clinical safeguards and collaboration, which I identify as future work.

E. Voice, cloning, ethics, legal

Is cloning a voice legal/ethical?
Legal with consent. A voice is biometric personal data, so I default to synthetic/licensed voices and demonstrated cloning only on AI-generated samples — no real biometric data in the build or study. If a user uploads a recording, they must confirm they have the right to use it, enforced on the server, not just the UI. I also refused to clone any real or celebrity voice in development.
Cloning a dead person's voice — they can't consent.
That's the deepest issue, and the ethics literature raises it directly as the "consent of the dead." My stance is that NinaivX is a tool the bereaved user controls, wrapped in a rights gate, transparency, and safety design. I don't claim to have resolved it — I've tried to build responsibly around a genuinely contested question.
Isn't a checkbox easy to lie about?
You're right, and I acknowledge it. A consent gate places responsibility on the user but can't verify the claim — stronger options like voice-ownership or liveness checks would be future work. My mitigation is that the default path uses synthetic voices, so cloning a real voice is an opt-in edge case, not the norm.

F. Design decisions & alternatives

Why not use RAG from the start?
I considered it — it's requirement C1. Within the timeframe, prompt-level grounding plus the air-gap gave usable results without the infrastructure and latency of a retrieval pipeline. My experiment then quantified exactly where prompt grounding falls short, which gives a measured baseline for a future RAG version — so deferring it was the right call and the evaluation justifies it.
Why turn-based voice, not real-time streaming?
Streaming would lower perceived latency but it's a substantial re-architecture and constrained by the managed mobile runtime. Instead I reduced latency within a request-response design — a brief voice mode, a faster synthesis model, a warm-up call, and backgrounding the memory update — getting a turn down from 8–9 seconds to about 2.5–4. Full-duplex is future work.
Why React Native / Expo and a hand-rolled router?
Expo lets one codebase run on any phone through Expo Go, which made remote user testing possible without an app-store release. The navigation is a single state value selecting the screen — more than enough for a handful of screens, and it keeps the dependency surface small.

G. Limitations & future work

What's the biggest limitation?
That prompt-level grounding doesn't fully stop the persona inventing personal facts it was never told — around 40% in my test. It's honest, and it points straight at the fix: document-grounded retrieval over a bereaved user's own uploaded letters and memories.
What would you do differently / next?
Design retrieval in from the start — the evaluation showed it's the missing piece. Then improve voice naturalness, which users flagged as the weakest point, add streaming voice and an avatar that users requested, and run a larger, longitudinal study with human raters and, eventually and carefully, genuinely bereaved participants.

H. Scope, contribution, novelty

What's actually novel here? Griefbots already exist.
Two things. First, making the core safety property a structural guarantee — the air-gap at the level of the agent graph — rather than a prompt instruction. Second, and unusually for this area, publishing an evaluation of the safety design. Existing commercial products like You Only Virtual offer open-ended generation with no documented safeguard and no published evaluation. NinaivX is generative but also grounded, transparent, open, and evaluated.
Is this research or just engineering?
Both. The engineering is the artefact, but the research contribution is the safety-by-construction approach and its empirical evaluation — a controlled experiment answering whether grounding measurably reduces hallucination, and a user study on how it's received. It translates recommendations from the ethics literature into a working, tested system.
How did you manage the project?
Iteratively — short cycles each delivering a working slice end to end, so there was always a runnable system and the riskiest unknowns surfaced early. That's how the latency and encoding problems came up while they were still cheap to fix. I ran the ethics application in parallel with the build so the study could start as soon as approval came through.

I. Broader / curveballs

Should we even build these? Isn't talking to a simulation of the dead unhealthy?
It's a fair and unresolved question — Hannah Fry called it "committing to a lie." My project doesn't claim to settle that. My argument is narrower: if these systems are going to be built — and the market shows they already are — they don't have to be the opaque, unconstrained products that dominate today. They can be honest about being AI, prevented by construction from inventing the person, private, and openly evaluated.
How do you prevent dependency / unhealthy attachment?
By design choices: no gamification, no streaks, no engagement-maximising mechanics — the opposite of the Replika-style patterns the literature criticises. And a persistent AI-transparency policy, so the user is always able to know they're talking to an AI. My study found comfort and satisfaction were high with no reported discomfort.
What if the model provider changes or the API goes down?
The voice provider is initialised lazily, so the app still runs and returns a clear "service unavailable" for voice if the key's missing, rather than crashing. The model layer is abstracted behind one helper, so swapping providers is a small change. Graceful degradation was an explicit requirement.
Can one user access another's persona?
No — every persona-scoped operation confirms ownership before returning anything, which closes the insecure-direct-object-reference risk. I have an automated test that hits all sixteen protected endpoints unauthenticated and confirms each returns 401.
Two lines to have ready no matter what
Headline: "Same model, only the grounding changed — hallucination dropped 83% to 25% overall, and post-death events from 100% to zero, with no cost to conversational quality and a 4.6-out-of-5 user rating."
Honesty line (use freely): "That's a real limitation — I acknowledge it in the report, and here's the future work that addresses it."
